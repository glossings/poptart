poptart, from scratch

A livecoding instrument that plays real plugins from terse patterns.

This is a guided tour — a handful of short studies that build on each other. Read them in order the first time and you'll come out the other side able to play. There's nothing to click along with here; keep the editor open in the other tab and try each idea as you meet it. Everything below is plain text you can paste and bend.

The one-sentence version: you write little patterns, poptart turns them into notes and knob-turns, and it sends those to actual VST/VST3 instruments and effects running inside a SuperCollider audio engine. No samples pretending to be a synth — the real thing, modulated continuously while it plays.

Study 0

The editor & the loop

The whole workflow is one gesture: type, then evaluate. Press Cmd/Ctrl + Enter to play what's in the editor; press Cmd/Ctrl + . to stop. Editing and re-evaluating swaps the running sound out from under itself without a gap — that's livecoding. There's an update button too, which re-evaluates without changing the play/stop state.

A buffer is split into blocks. A block that starts with a label — a name, then a colon, at the very start of a line — becomes one track: 

bass: note("c2 c2 g1 a1").synth("Serum 2")
drums: s("bd*4, ~ hh ~ hh")

Two labels, two tracks, playing together. The label is just an identifier — call it whatever you like. Lines that continue an expression (a .param(…) chain, a multi-line template) stay attached to the block above them, so you can spread one track across many lines.

Two decorations on a label change whether it sounds, without deleting the code:

  • A leading or trailing underscore mutes it: _bass: or bass_: go silent.
  • A leading or trailing capital S solos it: Sdrums: — if anything is soloed, only soloed tracks play (mute still wins over solo).

Code that isn't a labelled track — a bare line, or a block starting with $: — runs as setup: shared consts, language extensions, one-off statements. More on that in Study 10. A named block, by contrast, must evaluate to a pattern.

panels The sidebar has four tabs. session shows the live tracks and the macro knobs; sounds lists your scanned plugins, their parameters, and your samples; files saves and loads whole buffers (hit ＋ new to start a blank one); settings holds the audio device, sample folder, and the startup prebake file.

Study 1

Everything is a signal

Here is the single idea that makes the rest of poptart click. A signal is a value that changes over time. That's it. A melody is a signal. An LFO is a signal. A single unchanging number is a (boring) signal. They are all the same kind of thing, so they all compose the same way.

Some signals have edges — known moments where one value ends and the next begins. A note pattern "c e g" has three steps per cycle, so poptart knows exactly when to trigger each note-on and note-off. Other signals are smooth: an LFO has no steps, it's just sampled continuously wherever a value is needed. The same machinery reads both.

The unit of time is the cycle (a bar). Tempo is set with setbpm(120) — read as 4 beats per cycle, so 120 bpm is two cycles per second. Whatever you write inside a pattern string is laid out to fill exactly one cycle, then repeats.

Because signals compose, the interesting verbs are the ones that combine and reshape them — .add(), .range(), .when(), .mul() — and they don't care whether they're working on a melody, an LFO, or a knob. Keep the mental picture of "a value that changes over time" and the API stops being a list to memorise.

Study 2

Mini-notation: the string language

The strings inside note("…"), s("…"), .param("…", "…") and friends are their own tiny rhythmic language, borrowed from Strudel/Tidal. A space- separated list divides the cycle evenly: 

"0 1 2 3"        // four equal steps
"0 ~ 2 ~"        // ~ is a rest (a gap / gate-off)

The rest of the vocabulary, by example:

SyntaxMeans
[a b]Sub-group: the pair shares one step's worth of time.
a b, c dStack: comma layers voices that play at once.
<a b c>Alternation: one item per cycle, cycling round.
a*4Fast: repeat a four times inside its slot. The rate can be a pattern: a*<2 3> alternates it per cycle, a*[1 2] changes it mid-cycle.
a/2Slow: stretch a across two cycles. Patterned rates work here too.
a!3Replicate: three separate a steps.
a@3 bWeight: a takes 3× the room of b.
a _ _Tie: _ extends the previous note, so it holds.
1.e(3,8)Euclidean: 3 hits over 8 steps, as a value.method(...) postfix (on a sample: bd.e(3,8)). Each hit is legato — held until the next onset.
a? / a?0.3Degrade: randomly drop the step (30% here).
a|b|cRandom choice: pick one per cycle.
(<12 13>*4 + 5 * i(0,5))Expression: full mini-notation combined with + - * /. See below.
r / r(a) / r(a,b)Random float: [0,1] / [0,a] / [a,b].
i(a) / i(a,b)Random integer, inclusive of both ends.
p / p(a,b)Perlin-ish drift: value-noise that changes gradually across cycles.
round/floor/ceil(x)Rounding, e.g. (floor(r*12)).

These nest freely: "<[0 2] [3 5]>*2" is legal and does what it looks like. Inside (...) you can write full mini-notation and combine it arithmetically: operators bind tighter than the space that separates sequence steps, and each operator takes the left pattern's structure. Crucially *// stay fast/slow when glued to a value (2*4) but mean multiply/divide when spaced (2 * 4); put a space before a -. r i p round floor ceil are reserved names. One Strudel feature isn't in yet — polymeter {a b, c d}.

tip The randomness in ?, |, r, i and p is deterministic per cycle: a given bar plays the same each time it comes round, and the editor's playback highlight always agrees with what you hear.

Study 3

Notes, degrees, and scales

There are two ways to say which pitch you want, and it's worth being clear on the difference.

note(…) is absolute pitch. It takes note names or MIDI numbers: note("c4 e4 g4"), note("60 64 67"). The convention is c5 = 60 (middle C), the same as Strudel. Sharps and flats are c#4 / db4.

n(…) is scale degrees. The numbers are steps within a scale — 0 is the root, 1 the next note up, 7 the octave — and they mean nothing musical until you name the scale: 

n("0 2 4 6").scale("F minor")   // degrees → the notes of F minor

A scale name is "<root> <mode>": "F minor", "c dorian", "Bb mixolydian". Bare mode names default to root C. The usual modes, pentatonics, blues, harmonic/melodic minor, and chromatic are all there, with the common aliases (maj, min, m, …).

note-quantizing

.scale() now does the sensible thing for both kinds of pattern:

  • On a degree pattern (n(…)) it maps degrees to notes, as above.
  • On a note pattern (note(…)) it snaps each note to the nearest pitch in the scale, bending out-of-key notes into the key: 
note("c4 e4 f#4 g4").scale("C major")
// f#4 is not in C major → snaps to the nearest scale tone (f4). The rest are already in key.

This is the exact same snap poptart applies to live notes coming off a MIDI keyboard, so a played line and a written line land on the same pitches. Ties resolve downward.

Both builders work on either side of the instrument, and the pitch kind is remembered through arithmetic — note("c4 f#4").add(12).scale("C major") still knows it's holding notes, not degrees. A bare synth("…") with no notes plays a default C2 every cycle, so a fresh instrument makes sound immediately while you decide what it should play.

draw it

pianoroll("…", { grid, len }) is the same absolute-note pattern as note(…), but drawn. grid is the granularity (cells per cycle — the *grid of the equivalent mini-notation) and len is the loop length in cells, so { grid: 16, len: 3 } is a three-1/16-note loop. Click the word pianoroll and an Ableton-style grid opens over the editor, with a real piano keyboard down the side, a draggable loop bar along the top, and a playhead that sweeps the loop as it plays. (Only the name opens it — the arguments stay ordinary code you can edit by hand, and the roll follows along when you do.) Every change you draw is written back into the call and re-evaluated, so what you hear is always what's on screen. An empty pianoroll() is a valid empty roll — start there and draw.

Draw with the pencil (drag), or press B for the arrow tool to marquee-select; click to select (shift-click or ctrl/cmd-A for more), drag to move, drag the right edge to resize, cmd-drag up/down to set velocity (or flip the vel/prob toggle to set per-note probability, which becomes a ? degrade). cmd-D duplicates, arrow keys nudge (shift = octave / bar), delete removes, double-click erases one. Overlapping notes play as chords; the grid and len fields (or dragging the top loop bar) size it; cmd −/+ zoom; 🎧 auditions each note through the track's synth; and →♪ converts the whole roll to the equivalent multi-line <…>*grid mini-notation. 

pianoroll("60,0,4 64,0,4 67,8,8", { steps: 16 }).synth("Serum 2")
// each note is midi,start,len[,vel] over a `steps`-cell cycle. Chains like note(): .scale(), .add(), …

Study 4

Instruments & effects

.synth("…") loads a VST/VST3 instrument into the track; .fx("…") chains an effect after it (and after any earlier .fx()). The strings are the plugins' real names.

your rig, not mine This guide writes "Serum 2", "Diva", and so on as stand-ins. Substitute plugins you actually have. Open the sounds tab, hit rescan to scan your installed plugins, and click any result to copy its exact name — that copied string is what .synth() / .fx() want. Names also autocomplete as you type inside the quotes. 
lead: note("c4 e4 g4 b4")
  .synth("Serum 2")
  .fx("ValhallaDelay")
  .fx("Pro-Q 3")

Chain length maxes out at 8 slots (1 instrument + 7 effects) — a deliberate limit of how the audio engine is built.

Parameters

.param("<real VST name>", value) sets any knob on whatever plugin is currently last in the chain. There's no alias layer — you address the plugin's own parameter names directly: 

.param("Filter 1 On", 1)
.param("Filter 1 Freq", 0.6)

To discover names: evaluate once with the .synth(...) so the plugin loads, then open the params panel (sounds tab) — every parameter of every plugin in the chain, searchable; click one to copy it. Inside .param("…") the names also autocomplete.

A raw parameter value is normalized 0..1 unless a mapping file gives it real-world units. With a mapping in place, .range(200, 5000) on a filter cutoff means literal Hertz. Mapping files live in mappings/*.json and hot-reload each eval; one worked example (serum2.json) ships. Without a mapping, just think in 0..1.

duplicate names Some plugins reuse a name across sections (Diva has three params called Frequency). Plain .param("Frequency", …) hits the first; append the parameter index to pick one — .param("Frequency#95", …). The params panel and autocomplete show the #index form for you whenever a name collides.

For fiddly static sound-design settings (unison voices, wavetable position), click ui next to a plugin in the track panel to open its own editor window and set them by hand — then keep livecoding everything else.

Design a sound, share a link

Change anything in a plugin's own window — a knob, a preset from its browser — and its complete state is captured into the code for you, as the call's second argument: synth("Serum 2", { state: "H4sI…" }). Nothing to press, and until you touch it the bare synth("Serum 2") means "however the plugin defaults". Writes are debounced, so a knob sweep lands once when you let go, as one undo step. On every load that state is restored, so the patch sounds identical on a cold start. Because the whole buffer lives in the URL hash, sharing the link shares the exact sound. The editor folds the blob into a small {⋯} pill — click it to expand. lfo() shape strings and pianoroll() note strings fold the same way (they're editor-written data, not code to read), so a call stays one readable line however much it holds.

Study 5

Modulation: making it move

Any .param() value can be a number, a mini-notation string, an LFO, or an envelope. This is where poptart earns its keep — modulation runs natively inside the audio engine, sample-accurate, with no per-note network traffic.

LFOs

sine, saw, tri, square, plus ramp and rand. Each is a 0..1 shape; .range(lo, hi) rescales it. Set the speed with a rate in Hz: 

.param("Filter 1 Freq", sine({ rate: 0.3 }).range(200, 5000))
.param("Filter 1 Freq", sine(0.3).range(200, 5000))  // rate shorthand

lfo("…", { rate, mode }) is a hand-drawn shape. Click the word lfo in the editor and an interactive shape editor opens — drag points, bend segments — writing the breakpoint string for you and re-evaluating as you go, so the modulation follows the curve. (Only the name opens it; the arguments stay ordinary code, and the panel follows along when you edit them by hand.) Modes: free (its own clock), retrigger (phase resets on each note), envelope (plays once per note then holds).

Envelopes

env({ attack, decay, sustain, release, curve }) is an ADSR retriggered by the track's own notes — a per-note filter or mod envelope, times in seconds, sustain 0..1. .range() scales it like an LFO: 

.param("Filter 1 Freq", env({ attack: 0.01, decay: 0.3, sustain: 0.2 }).range(300, 6000))

An envelope's value only exists inside the engine (it depends on note gates), so you can't do arithmetic on it in JS — shape it with .range() and the curve option instead.

Macros & MIDI knobs

The macros panel gives you eight knobs, pre-bound in code as macro1…macro8 (also macro(3)). Drop one anywhere a signal goes for a hands-on control: 

.param("Filter 1 Freq", macro1.range(200, 4000))

midicc("<device>") turns a hardware controller into a signal source: const cc = midicc("Twister"); … cc(12, 1).range(0, 1) is CC 12 on channel 1. Assigned to a param it binds natively — a real knob driving a real knob, no polling lag.

signal bounds .range()'s bounds can themselves be signals: lfo().range("200 300", 4000) sweeps from a stepped floor. (Signal bounds move that modulator onto the polled path, since the native oscillator takes only fixed lo/hi — still musical, just not sample-accurate.)

Study 6

The channel strip

Three controls live on the track's output stage, after the whole plugin chain. They take numbers, mini strings, or any signal:

MethodDoes
.gain(v)Output level (1 = unity). Chains multiply: .gain(0.5).gain(env()) is a base level times a VCA.
.pan(v)Stereo pan, −1 (left) … 1 (right), 0 = centre.
.o(n)Which output pair: .o(1) = channels 1/2, .o(2) = 3/4, wrapping past the device's last pair.
pad: note("c3 e3 g3").synth("Diva")
  .gain(0.7)
  .pan(sine(0.2).range(-1, 1))    // slow auto-pan

Study 7

The sampler

s("pack") plays a folder of audio files — a pack — from your sample library (default ~/.poptart/samples; set it in the settings tab). Files are addressed by index in filename order, and everything runs through the same .fx()/.param() chain as an instrument: 

drums: s("bd*4, ~ hh ~ hh")   // "bd:4" picks a file inline = s("bd").i(4)
  .i("<0 1 2>")          // which file of the pack (Strudel's n, renamed)
  .begin(0).end(1)          // play region, 0..1
  .loop()                   // loop the region instead of one-shot
  .speed("1 -1")           // playback rate; negative = reversed
  .stretch(2)               // granular timestretch (pitch preserved)
  .slice("0 1 2 3")         // play the nth transient (WAV only)
  .note("45 _ 52 57")       // repitch by MIDI note (24 / "c2" = as recorded)
  .vel("1 .5 ~ 1")          // per-event volume (also on synth tracks: MIDI velocity)
  .adsr(0.1, 0.2, 0.6, 0.2) // amplitude envelope, as multiples of the note length

On a sampler, .note() / .n() repitch the sample instead of choosing an instrument note — and .scale() applies exactly as in Study 3 (degrees map, absolute notes snap to key). Sampler events are always gated: a sample rings for exactly its event length and is cut there, so a bare s("longsample") chops at each cycle rather than piling up. To let it ring longer, make the event longer: s("long/2"), "long@2", or ties.

Patterned .note()/.vel()/.slice() are structural — each fresh step retriggers, a ~ drops the event — so you can carve a melody or a beat out of a single sample.

Study 8

Playing live

Three ways to play a track by hand, in real time, alongside the patterns:

SourceWhat it is
midikeys("<device>")A MIDI keyboard. midikeys("KeyStep")(1).synth("Serum 2") plays channel 1 live — notes, velocity, pitch bend, aftertouch, CCs — routed engine-side, so latency is the MIDI driver's, not the pattern clock's.
keyboard()Your computer's typing keyboard as a piano: home row = white keys, the row above = black keys, z/x shift octave, c/v nudge velocity.
tap()Like keyboard(), but every key fires the track's default note — the whole keyboard becomes one velocity-sensitive pad. Great for drums and stabs.
keys: keyboard().synth("Serum 2").scale("F minor")

For the computer keyboard, flip the ⌨ switch in the header: off types normally, midi plays notes and suppresses typing, both does each at once. Live notes gate env() modulators and retrigger note-synced lfo() shapes exactly like pattern notes — and .scale() on a live source quantizes incoming notes to the key.

recording The header's ● rec button captures MIDI-key playing back into the pattern: it arms now and starts on the next 4-cycle phrase, quantizing to the grid you pick. What it writes is an ordinary pattern string you can then edit by hand.

Study 8½

Routing: midi() & audio()

Two builders, midi() and audio(), move MIDI and audio between inputs — another track, or a piece of hardware — and your tracks and plugins. Each works in two positions, and that position decides what it does.

As a source, at the head of a track

A bare midi(...) / audio(...) is where a track's signal comes from:

midi("KeyStep 32").synth("Serum 2")     // play Serum from a MIDI device's notes
audio("Scarlett Input 1").fx("ValhallaRoom") // run a hardware input through a reverb

As an injector, after a plugin

Called as a method after an .fx(...), it feeds that plugin's extra input:

bass: note("c2*8").synth("Serum 2").fx("Kickstart").midi("kick")  // duck to kick's rhythm (MIDI trigger)
bass: note("c2*8").synth("Serum 2").fx("Pro-C 2").audio("kick")   // Pro-C's sidechain listens to kick (audio)
kick: s("bd*4")

.midi("kick") injects MIDI into the plugin — a track source replays its notes (a drum track fires a fixed note on each hit, a melodic track passes its pitch through), so a MIDI-triggered ducker like Kickstart follows the rhythm. .audio("kick") feeds the source's audio into the plugin's sidechain input, for audio-keyed compressors/duckers (Pro-C 2, ShaperBox). Both target whatever plugin is last in the chain, like .param().

Names: tracks or hardware

The argument to any of these is a name, resolved track-first: if a track with that label exists it wins; otherwise it's matched against connected devices (case-insensitive substring). Force either with a prefix:

NameMeans
"kick"the track labelled kick (or a device, if no such track)
"track:kick"always the track
"dev:KeyStep"always a hardware MIDI/audio input
tip For a plain MIDI-note trigger with no dedicated track, make a muted one and point at it: _trig: note("c5 ~ c5 ~") then …​.fx("Kickstart").midi("trig"). A leading underscore mutes the trigger track so you only hear its effect on the target.
note Audio routing runs the source ahead of the target in the engine so the send is heard the same instant. Hardware audio input depends on your audio device actually exposing inputs (many output devices have none) — pick an input-capable device in settings.

Study 9

Transforms & combinators

Since patterns are signals, you reshape them with methods. Arithmetic takes its structure from the left side, so the right can be a number, a string, or another signal: 

note("c3 e3 g3").add(12)          // up an octave
n("0 2 4").add("<0 7>").scale("C major")  // transpose every other cycle

Full set: add sub mul div mod round abs floor ceil clamp, and comparisons gte gt lte lt eq neq (which return 1/0, handy as conditions).

MethodDoes
.fast(f) / .slow(f)Playback rate: .fast(2) fits two cycles into one, .slow(2) spreads one over two. A negative factor plays the pattern in reverse — .fast(-1) is straight reverse playback. On an LFO, .fast() multiplies its rate (.rate() sets it absolutely).
.when(cond, fn)Apply fn to this pattern wherever cond is truthy, on cond's own grid. n("0 1 2 3").when("1 0".gte(1), x => x.add(12)).
.degrade(p)Randomly drop each event with probability p (default 0.5). The ? in mini-notation, as a method.
.ply(n, fn?)Retrigger each event n times; optional (x, i) => … transforms each repeat.
.echo(n, dt, fn?)Overlay n delayed copies, each dt cycles further along — a pattern-level tape echo.
.hold(trig)Sample-and-hold: freeze this signal at each onset of trig. rand().hold("1*8") is stepped random.

And choose("0", "3", "5") is a signal that randomly picks one option per cycle — weight a pick with a [value, weight] pair. It drops in anywhere a signal goes: n(choose("0", "3", "7")), .speed(choose(0.5, 1, 2)), s(choose("bd", "hh")).

Study 10

Making it yours

Extend the language

Signal.prototype is the shared prototype of every pattern, LFO, and mini string. Add a method to it and every signal — and every bare string — picks it up, right from the editor, exactly like Strudel's Pattern.prototype: 

Signal.prototype.acid = function () {
  return this.param("Filter 1 Freq", 0.3).param("Filter 1 Reso", 0.8);
};

bass: note("c2*8").synth("Serum 2").acid()

These Signal.prototype.… and const … lines are ordinary setup statements: put each on its own column-0 line anywhere in the buffer, between tracks or above them. (A bare $: Signal(0.5) is not setup — it evaluates to a signal, so it becomes a silent track. To reuse a value, name it: const half = Signal(0.5).)

Prebake: setup that runs at startup

Anything you'd paste at the top of every session — helpers, custom scales, prototype extensions — goes in the prebake, run once at load before any pattern plays. Edit it from the settings tab (edit prebake…; saving re-runs it, no restart) or in ~/.poptart/prebake.js: 

// ~/.poptart/prebake.js
const kick = s("bd*4");
const acid = (p) => p.param("Filter 1 Freq", 0.3);

Its top-level bindings are injected into every buffer afterward, so drums: kick or bass: acid(note("c2*8").synth("Serum 2")) just work. For more, add a ~/.poptart/prebake/ folder of *.js files (they run in filename order). Removing a prototype extension needs a restart; everything else re-runs on save.

Write your own functions

Inside a method, this is a signal and you return one — chain the same methods a pattern has (.add/.mul/.range/.when/.hold/.gain/.param/.mapValue, and the rest). For pitch math, three helpers are exposed by name everywhere: noteToMidi("c4") (note name → MIDI), degreeToMidi(degree, "c minor") (scale step → MIDI, wrapping past the scale), and parseScaleName("f dorian") (→ { rootMidi, intervals }). 

// a chord builder: intervals above a root, stacked into one mini "," layer
const chord = (root, ...ivs) =>
  note(ivs.map((iv) => noteToMidi(root) + iv).join(","));

pad: chord("c3", 0, 4, 7, 11).synth("Serum 2")   // Cmaj7

Hotkeys & editor scripting

The prebake runs in the browser too (DSL builders are inert there; the UI helpers are live), so it's where you bind keys and script the editor. Register a chord with hotkey(combo, handler): 

// rotate the selected space-separated steps by one
hotkey("alt+r", () => {
  const { from, to, text } = editor.getSelection();
  editor.replaceCode(rotate(text.trim().split(/\s+/), 1).join(" "), from, to);
});

Combos are +-joined: modifiers cmd/ctrl/alt/shift/mod (mod = ⌘ on macOS, Ctrl elsewhere) plus one key, matched on physical key position. The editor handle (aliased repl) reads and rewrites the buffer by character offset — getCode/setCode, insertCode/replaceCode, getSelection, getCursorLocation/setCursorLocation — and the sandbox also hands you prompt, alert, log, and the rhythm helpers bjorklund, rotate, clamp. Built-in ctrl+p/ctrl+r/ctrl+m are reserved.
